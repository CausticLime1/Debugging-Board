# sharkbyte

STM32H723 firmware for the SharkByte board.

## Prerequisites

- **Windows** (the build toolchain runs via PowerShell)
- **VSCode** with the [STM32 VSCode Extension](https://marketplace.visualstudio.com/items?itemName=stmicroelectronics.stm32-vscode-extension) installed
- **STM32CubeMX** 6.15.0+

## Getting started

### 1. Clone

```bash
git clone --recurse-submodules <repo-url>
```

### 2. Regenerate CubeMX files

Most of the ST-generated HAL and middleware files are not checked in — they're derived from `sharkbyte.ioc`. Regenerate them with:

**Command Palette → Run Task → STM32: CubeMX Codegen**

Or from the terminal:
```powershell
powershell -File .vscode/stm32cube.ps1 codegen
```

### 3. Build

**Command Palette → Run Task → STM32: Build Debug**

Or:
```powershell
powershell -File .vscode/stm32cube.ps1 build
```

### 4. Flash

Connect an ST-Link and run:

**Command Palette → Run Task → STM32: Flash And Run Debug**

This builds, flashes, and resets the board.

## Project structure

```
sharkbyte.ioc       # CubeMX project — source of truth for chip config
CMakeLists.txt      # Top-level build (manually maintained)
Core/Src/main.c     # Application entry point
Core/Src/encoder.cpp
Core/Inc/
gui/                # LVGL UI code
.vscode/
  stm32cube.ps1     # Build/flash/codegen script
  tasks.json        # VSCode task definitions
```

## Notes

- `Drivers/`, `Middlewares/` are gitignored — they are regenerated by CubeMX and should not be edited by hand
- The ST bundle versions (compiler, CMake, etc.) are pinned in `.settings/bundles-lock.store.json` and downloaded automatically by the ST extension on first open
- USB init function is disabled in CubeMX

### Linker script

The build uses `STM32H723XG_FLASH_custom.ld` (not the CubeMX-generated `STM32H723XG_FLASH.ld`). The custom file differs in three ways:

- `FLASH` region trimmed from 1024 KB to 896 KB (sectors 0–6)
- `NV_STORAGE` region added at sector 7 (`0x080E0000`, 128 KB) for persistent settings
- `.dma_buf` section placed at a fixed address in RAM_D1 (`0x24010000`, after the 64 KB LVGL heap) — LVGL draw buffers must live in the CPU's D1 domain to avoid the STM32H7 D1→D2 interconnect write-buffer coherency issue with DMA1

CubeMX regeneration overwrites `STM32H723XG_FLASH.ld` but does not touch the custom file. If the device config changes in a way that affects flash or RAM layout (e.g. stack/heap sizes), diff `STM32H723XG_FLASH.ld` against `STM32H723XG_FLASH_custom.ld` and merge any relevant changes manually.
